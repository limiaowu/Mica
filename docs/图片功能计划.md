# 图片功能计划

> 对标 [表格HTML改造计划.md](表格HTML改造计划.md)。记录图片功能的设计决策、分期任务、关键约定，防止对话 compact 后丢上下文。
> 实现细节/踩坑随做随补到 [编辑器实现笔记.md](编辑器实现笔记.md)，本文件只管「设计与进度」。

## 总体决策（已与用户确认）

1. **混合序列化（2026-06 定稿，优于「一律 HTML」）**：自定义 image 节点覆盖 commonmark image。
   - **普通图（无 width/align/radius/border）→ 干净的 `![alt](url "title")` Markdown**；**带样式的图 → `<img …>` HTML**。
   - 理由：表格必须 HTML（合并单元格无 Markdown 等价），但图片不必——绝大多数粘贴的普通图保持 .md 干净，正好对症「不想每张图都变丑 HTML」的顾虑。
   - 用户手敲 `![]()` → input rule，闭合 `)` 时升格为图片节点（同行内代码「闭合触发」套路）。
   - 带样式 `<img>` 往返：`micaImageRemark`（$remark）把 html 节点还原成 mdast image（width/align 暂存 node.data，parseMarkdown 读出）。

2. **显示管道 = WebResourceRequested 拦截（host 喂文件流）**。这是地基，决定能否显示任意位置的本地图。
   - **为什么必须**：编辑器挂在 `https://editor.mica.local` 这个 https 源，https 页面里 `<img src="file:///...">` 会被 WebView2 安全策略拦掉 → 裂图。
   - **方案**：host 注册 `AddWebResourceRequestedFilter("https://img.mica.local/*", Image)` + `WebResourceRequested`，拦截后从磁盘读字节流返回。任意绝对路径都能显示，无需 base64，无需关心笔记本边界。
   - **URL 约定**：web 端 `<img>` 的 DOM src 永远是 `https://img.mica.local/img?p=<encodeURIComponent(绝对路径)>`。host 解析 `p`、`Path.GetFullPath` 规范化、读文件、按扩展名给 Content-Type 返回。

3. **存储位置 = `.mica/assets/<笔记相对路径去扩展名>/`（默认，已确认）**。
   - 放 `.mica` 下：目录树已自动隐藏 dotfile（`FileService.ScanDirectory` 的 `name.StartsWith('.')` 跳过），不污染树、不臃肿。
   - **每篇笔记独立子文件夹**（按笔记相对路径去扩展名建目录，天然避免同名冲突）：不搞全局共享池/去重，避免引用计数+hash 这套「迷你数据库」（违反「不做数据库」）。
   - 例：笔记 `日记/2026.md` 的图 → `<笔记本根>/.mica/assets/日记/2026/clip.png`。
   - **为什么 `.mica/assets/<note>/` 而非 `.mica/<note>.assets/`**：`.mica` 以后可能放别的功能文件夹，让 `assets` 作为其下一级、与未来兄弟文件夹平级，更清晰（用户授权我定）。
   - **.md 里存相对路径**（相对 .md 文件，如 `../.mica/assets/日记/2026/clip.png`，正斜杠）：可移植，别的渲染器也能按相对路径解析到真实文件。

4. **两个硬要求（用户提）**，靠在 `FileService` 删除/移动操作里联动资产文件夹保证：
   - **软件内删除笔记 → 连带删 `.mica/assets/<note>/`**。
   - **移动笔记到另一个笔记本 → 资产文件夹跟着搬**（不丢图）。
   - 注：用户手动在资源管理器里搬不管；只保证软件内操作不丢。

5. **图片存储模式设置项**（对标 Typora 下拉，存 `SettingsService.ImageStorageMode`）：
   - `0` 不复制（用原绝对路径） / `1` 内嵌 base64 / `2` 当前目录（与 .md 同级） / `3` `assets/` 子文件夹（与 .md 同级） / `4` `.mica` 统一管理（**默认**）。

## 缩放 / 对齐哲学（已确认）

- 显示宽度用**行宽百分比**（min 20% ~ max 100%），存 `style="width:60%"`，窗口变化天然自适应。
- **不加横向滚动条**（同表格窄表自适应，保持简单）。「100%」= 占满行宽，不纠结原图物理像素。
- 浮动条上做**宽度滑块 + 左中右对齐**（同表格整表宽度/对齐段）。

## 裁剪（已确认思路，放后期）

- **不动原图，只记「显示哪一块」**（存裁剪矩形，CSS `object-fit/object-position` 或 wrapper `overflow:hidden`）。可无限次回原图重裁。
- 裁剪面板用 WinUI 弹窗（可拖拽选框的 Canvas）。

### 第一期实测反馈与修复（2026-06，第二轮）
用户实测后修的 bug（均已改 + 编译通过，待复测）：
- **图片右侧超出行宽**：图片容器在某些布局下被算得比文本列宽 → `.mica-image` 的 `max-width` 改为 `min(100%, var(--mica-editor-width))`，双闸钉死绝不超行宽（editor.css）。
- **拖入图片无效**：ProseMirror 对「外部文件拖拽」默认不 preventDefault dragover → 浏览器拒绝放下、handleDrop 不触发。createEditor 给 wysiwygEl 加 `dragover` 监听，对含文件的拖拽放行。
- **退格删图体验**：`enterEmbedOnBackspace` 纳入 `image` → 退格先选中（NodeSelection 显描边）、再退格才删（同行内公式/代码）。
- **删笔记时 .mica 资产没进回收站**：疑因被删笔记标签还开着、WebView 占用图片 → 回收失败被吞。改为 `DeleteNodeAsync` **先 `CloseTabsUnder` 关标签再删盘**；`DeleteNoteAssets` 返回删掉的目录、调用点记 `Log.Information` 便于核查。
- **不算 bug（已向用户解释）**：① 文件名沿用原图名（如 `你的名字3.jpg`）、仅无名剪贴板位图才用 `image-时间戳`，这是有意的；② 手敲 `![测试]()` 空 url 不触发升格（要真实 url 才升格），空括号停留为文本并被 markdown 转义反斜杠是标准行为。

### 第一期实测反馈与修复（2026-06，第四轮）
- **图片节点从「行内」改为「块级」（重要架构变更）**：根因——行内图片右侧有个「行内光标位」，整图占满行宽时它换行到图片下方、渲染成一条**常驻空行**（上下移光标甩不掉，用户反馈 2）。改 `imageNode` 为 `group:'block'` 块级 atom 后图片不再待在段落里，无此残影。连带改动：
  - `toMarkdown` 普通图包一层 `paragraph`（块级图在 md 里=独占一行的图片段落）；带样式图存块级 `<img>` HTML。
  - `micaImageRemark` 新增 `splitParagraph`：把段落里的 image / `<img>`html **拆出为块级兄弟**（文本归文本段、每图独立成块），blockquote/列表项内同理递归。否则块级 image 待在段落里非法、解析失败。
  - 插入改 `replaceSelectionWith(块级image)`（不再包段落）；`enterEmbedOnBackspace` 把 image 并入「上一块是块级 atom（公式块/图片块）→ 退格先选中」分支，删掉行内分支与「仅含一张图的段落」分支。
- **拖入显示禁止光标、放不下（反馈 1）**：`dragover` 只 `preventDefault` 不够，浏览器默认 `dropEffect=none`。补 `e.dataTransfer.dropEffect='copy'` → 显示可放入光标并真正触发 drop。
- **复制图片粘不出 / 在资源管理器只打开桌面（反馈 4、5）**：同一根因——web 传来的绝对路径是「正斜杠+未解析 `..`」（如 `F:/a/日记/../.mica/x.png`），`explorer /select` 与部分文件 API 不认。宿主 `ShowImageContextMenu` 收到后先 `Path.GetFullPath` 规范化。复制图片另改用 `StorageFile + SetBitmap(CreateFromFile) + SetStorageItems + Clipboard.Flush()`（MemoryStream 流方式部分场景不进系统剪贴板）。
- **文件名时间戳（反馈 3）**：与用户商定**不做**——沿用原图名 + 同名数字去重更可读，时间戳无必要。

### 第一期实测反馈与修复（2026-06，第五轮）
- **拖入仍显示禁止号、放不下（反馈 1）**：`dragover` 用 `items.some(kind==='file')` 判断在 Chromium「保护模式」下拿不到 items 内容 → preventDefault 没执行。改用 `Array.from(dt.types).includes('Files')`（types 始终可读）+ 移到**捕获阶段**抢在 ProseMirror 前 preventDefault + 设 `dropEffect='copy'`。
- **图片块前点击出现「双光标」（竖线+横线，反馈 2）**：首块就是图片块时，点其前面是 gapcursor（横线，正常），但浏览器还叠了个原生竖线 caret。gapcursor 元素仅在该选区存在时才进 DOM，故 `.ProseMirror:has(.ProseMirror-gapcursor){ caret-color:transparent }` 命中时透明掉原生 caret，只留横线。
- **图片外加包装层 `.mica-image-wrap`（span，为二期浮动条铺路 + 实现红色覆盖）**：toDOM 改 `['span.mica-image-wrap',['img.mica-image']]`。wrap `width:fit-content` 收紧到图片尺寸 + 承载对齐(margin) + `position:relative`；img `width:100%` 填满。parseDOM 仍匹配内层 img、读 data-src/align。
- **选中图片改红色提示（反馈 3）**：`.mica-image-wrap.ProseMirror-selectednode` 红色 outline + `::after` 半透明红覆盖层（`rgba(229,57,53,.28)`，明暗都看得清、不过深）。覆盖层挂 wrap 的 ::after（img 替换元素不渲染伪元素）。点击/退格选中都红，明显区别于文本选区蓝色。

### 第一期实测反馈与修复（2026-06，第六轮）
> ⚠️ 本轮的「改回行内」在第七轮又被推翻，节点模型最终定稿为**块级**，见下。
- **图片节点改回「行内」（推翻第四轮的块级）**：用户要 Word/Typora 式**竖线光标**（图前=在前输入、图后=在后输入），块级节点点图前/后是**横线 gapcursor**、用户不接受。故 `imageNode` 恢复 `inline:true/group:'inline'`；toMarkdown 不再包 paragraph；micaImageRemark 恢复「块级 `<img>`html 包进段落、行内就地换」。
  - **常驻空行**（曾因块级/`display:block` 残留）这次靠 wrapper 用 `inline-block`（非 block）解决：图后只有光标真停过去时才临时换行（竖线，符合 Word），不再残留空行。代价：并排多图时光标位置有歧义——用户接受。
- **wrapper `.mica-image-wrap` 用 inline-block**：`max-width:100%`（父段落已是文本列宽=行宽，无需再钉绝对值）、`vertical-align:bottom`；img `max-width:100%`+圆角。独占一行居中靠 `p:has(>.mica-image-wrap:only-child){text-align:center}`（+ data-align 左/右变体）。
- **选中状态分两种（反馈 4，之前理解错了）**：① **点击选中** = 系统主题色（蓝）描边（普通 `ProseMirror-selectednode`）；② **退格预删** = 红框 + 半透明红覆盖层。靠新插件 `imagePendingDeletePlugin`（PluginKey 记「被退格选中的图片 pos」，加 `mica-pending-delete` node 装饰）区分——两者都是 NodeSelection 无法靠选区类型分。`apply` 用 `tr.selectionSet` 判定：带本 meta（退格）保留红；任何其他显式重设选区（点击/方向键/删除）清红。**圆角之前误删、已补回**。
- **红框下边被下方图片盖住（反馈 2）**：选中/预删的 wrapper 加 `z-index:1`（配 position:relative）抬到相邻图之上。
- **拖入图片暂时下线（反馈 3）**：删掉 `handleImageDrop` + handleDrop 接线 + dragover 监听（WinUI3 WebView2 宿主放行外部拖放有坑，以后用 XAML 层 drop 再做）。**粘贴仍可用**。

### 第一期实测反馈与修复（2026-06，第七轮）块级（⚠️ 已被第十一轮推翻，最终是「行内」，见文末）
> ⚠️ 本轮当时定「块级」，但第八~十轮在块级上 bug 不断，**第十一轮最终回到行内并定稿**。下面块级内容仅作历史，别照做。
- **图片节点定稿为「块级原子」**：行内方案的硬伤——wrapper 无论怎么调都会在图后残留「常驻空行」、且破坏居中（第六轮 `inline-block` 也没彻底根治，用户实测又复现）。竖线光标虽好但不值得这两个 bug。用户拍板：**改回块级，竖线光标这事就放弃**（图前/后是横线 gapcursor，接受）。
  - `imageNode`：`group:'block'`、去掉 `inline/marks`，atom/selectable/draggable 不变。toDOM 外层 `span`→`div`。
  - **序列化**：普通图 toMarkdown 用 `openNode('paragraph')` 包住 image 再 close（mdast image 是 inline phrasing，裸块会丢），仍输出独占一行的 `![]()`；带样式图直接块级 `<img>` HTML。
  - **micaImageRemark（反序列化）**：改成「把段落里的 image 提升为块级兄弟」——`paragraph[image]`→裸 `image` 块；`paragraph[文字 image 文字]`→拆成 `段落 / image / 段落`（提升后留下的纯空白段丢弃）；块级 `<img>`html 直接转 image 块。
  - **输入规则** `![]()`：`replaceWith`→`replaceRangeWith`（块级节点塞进段落要靠它拆分段落容纳，`replaceWith` 会抛错）。
- **CSS**：`.mica-image-wrap` 由 `inline-block` 改 `display:block; width:fit-content; margin:0.6em auto`（默认居中），`[data-align=left|right]` 用 margin 推到一侧。删掉行内方案的 `p:has(...){text-align}` 居中规则 + `caret-color:transparent` 双光标 hack（块级用 gapcursor 是预期，无双光标）。圆角保留。
- **退格预删红框**（沿用第六轮 `imagePendingDeletePlugin`）适配块级：`enterEmbedOnBackspace` 第一分支保留 `image`（图后 gapcursor 退格时 `nodeBefore` 即图块）；第二分支由「上一段落仅含一图」改判「上一个块就是 image」。点击=蓝、退格=红+覆盖 的两态不变。
- **边框圆角 vs 图片圆角（用户问 2）**：用户说的是**边框**的圆角，但边框功能本身是二期、目前还没做（现在只有 img 的 `border-radius:2px`）。计划：二期做边框时，把图片圆角与边框圆角**统一成同一变量**，选中框/覆盖层也跟着圆，贴合更好。
- **多图并排/九宫格（用户问 3）**：现在的单图块级原子节点已是好基座，无需为此改它。图片组是**独立容器节点**（phase 4），块级 image 作其子节点即可，现在不必预先建模——留到 phase 4 单独设计（避免过度抽象）。

### 第一期实测反馈与修复（2026-06，第八轮）光标模型收尾（仍是块级）
> 块级模型的两个光标 bug，根因都已锁死、修法确定。模型不变（块级），不再动摇。
- **图下方空行删不掉（反馈 1，根因）**：块级图下方的空段落，退格时 ProseMirror 默认就是「选中上面的原子块」而非删空行，叠加上轮「上一个块是图就红选」→ 空行永远删不掉。修：`enterEmbedOnBackspace` 里「上一块是 image」分支再分两路——**当前段落为空** → `tr.delete` 删掉该空段落，光标用 `GapCursor`（图后是块/末块）或 `Selection.near` 落到图后空隙；**非空段落行首** → 维持红选预删。注：文末那一行空段由 `trailing` 插件保证、删不到只剩它是正常的（要留位置在末尾续写）。
  - `GapCursor.valid` 运行时存在但 milkdown 类型再导出丢了静态签名 → 受控 cast 调用。
- **图在文首点其前方出现双光标（反馈 2，复发）**：gapcursor 横线 + 浏览器原生竖线 caret 叠加。第七轮把治它的 `.ProseMirror:has(.ProseMirror-gapcursor){ caret-color:transparent }` 误删（以为只行内需要）→ 复发。**补回**（块级同样需要）。
- **光标模型的话术（答用户问 3）**：竖线 = 在文字里；横线 gapcursor = 块对象之间的空隙。真正「竖线贴图两侧」必须行内，但行内的空行/居中两轮没根治、风险高；块级的光标问题已全部锁死可控，故定块级（用户认可放弃竖线贴边）。多图横排 = phase 4 图片组容器，不靠堆块。

### 第一期实测反馈与修复（2026-06，第九轮）⭐ 自绘竖线光标（块级模型最终形态）
> 块级 + 自绘光标，鱼和熊掌兼得：保留块级（无幻影空行、居中），同时给出 Word 式竖线光标。
- **核心洞察（用户提出）**：块级图片两侧的插入点本就有个「不选中节点的中间态」= ProseMirror 的 **gapcursor**，只是默认渲染成横线。把它**改渲染成图片左/右边缘的竖线**，并接管它的键，就同时拿到：竖线指示 + 能到图前删上方空行 + 图后退格选中图 + 图片只在显式操作时被选中。
- **自绘竖线**：`imageGapCaretPlugin`（`web/src/editor/createEditor.ts`）——光标是「紧邻图片的 gapcursor」时，① `props.attributes` 给编辑器根加类 `mica-img-gap`（CSS `display:none` 默认横线 gapcursor）；② `props.decorations` 给图片节点加 `mica-caret-before/after`，CSS 在 `.mica-image-wrap` 左/右边缘画整高闪烁竖线（复用 `ProseMirror-cursor-blink` 动画）。`.mica-image-wrap` 本就 `position:relative`，竖线用 `::before/::after` 绝对定位。
- **统一键处理** `handleImageKeys`（在 `handleKeyDown` 最先调，命中即拦）：
  - **gapcursor 图前竖线**：退格删图前面的块（**上方空行**，解决「到不了图前删不掉空行」）；前删/Delete → 选中图（红）；→/↓ 跳到图后竖线。图在文首无上方内容则吞掉退格、不误删图。
  - **gapcursor 图后竖线**：退格 → 选中图（红，解决「文末图后孤立空行退格无反应、也选不中图」）；Delete 删图后面的块；←/↑ 跳到图前竖线。
  - **选中态（NodeSelection）按方向键** → 移到图旁竖线、取消选中（用户：移动光标到图旁不该一直选中）。
  - **文本选区在块边缘按 ↑/↓ 走向图片** → 用 `view.endOfTextblock('up'/'down')` 判在边缘 + 下/上一个顶层块是 image → 落到图旁竖线（**而非选中图片**，这是「我一向下移动就直接选中图片」的修复）。仅处理 `depth===1` 顶层图。
  - **空段相邻图片的增删**：段首退格且上块是图——中间多余空行（空段且其后还有内容）→ 删掉、落图后竖线；其余（非空段首/文末空段）→ 选中图（红）。空段 Delete 且下块是图 → 删掉这个空段（图上方空行）、落图前竖线。
  - 落光标统一走 `gapOrNear`：能放 gapcursor（图旁/两图间）就放，否则 `Selection.near`（下一块是文本则落其开头，也是竖线）。
- **enterEmbedOnBackspace 移除全部 image 分支**（第七/八轮的图片退格逻辑），图片键全归 `handleImageKeys`，避免两处打架。
- **双光标 CSS（`caret-color:transparent`）保留**：自绘竖线是我们画的，原生 caret 仍要透明掉。
- **遗留**：`handleImageKeys` 只处理顶层（`depth===1`）图片，列表/引用内的图片光标走默认（gapcursor 横线）——目前图基本都在顶层，够用；将来若要支持嵌套图再扩展。

### 第一期实测反馈与修复（2026-06，第十轮）⭐⭐ 光标/选中框模型定稿 + 去 trailing
> 第九轮的自绘竖线几乎出不来（根因见下），且用了不稳的 PM 接口。本轮先把模型彻底想清楚再重写，并移除 trailing。

**模型（块级图片的光标与选中框，三问三答）：**
- **选中框（蓝/红）是什么**：表示「图片本身是当前操作对象」——删除/对齐/替换。**只有点击图片**（蓝）或**退格/前删"撞进"图片**（红，预删）才出现。选中时按方向键即松开成图旁光标、取消选中。
- **光标何时出现、在哪**：永远表示「文字插入点」。① 图上/下方**有段落**时，光标就在那段落里（上段末/下段首），是正常文本竖线；② 图在**文首/文末/两图相邻**（旁边没段落）时，光标是 gapcursor，自绘成图左/右边缘的竖线（`mica-caret-before/after`）。
- **怎么删相邻空行 / 不被图片黏住**：见下键处理；核心是「空段紧邻图片就直接删空段」，且**去掉 trailing**（文末不再强制留空段），图片可作真正的最后一块。

**第九轮根因（已修）**：自绘竖线只在「光标是 gapcursor」时画，但图旁一旦有段落（含空段），该位置被段落文本光标占了、根本没有 gapcursor → 竖线几乎出不来；且 `Selection.near` 在只剩原子时会「选中」图片（方向键误选根因）、`endOfTextblock` 判边缘不稳。

**本轮重写 `handleImageKeys`（稳，不用 Selection.near/endOfTextblock/GapCursor.valid）：**
- 落点统一走 `placeCaret`：相邻是文本块→落进文本块（正常竖线）；否则 `new GapCursor`（图旁竖线）。**绝不** Selection.near。
- ① 选中图片态 + 方向键 → 松开成图旁光标。
- ② gapcursor 图前竖线：退格删图前块（上方空行，文首无内容则吞掉不误删）；Delete→选中图（红）；→/↓ 跳图后。图后竖线：退格→选中图（红）；Delete 删图后块；←/↑ 跳图前。
- ③ **空段紧邻图片**（上块或下块是图）+ 退格/Delete → 直接删这个空段、落到图旁竖线。**这是「图上/下空行删不掉」的正解**，只认「本段为空 + 邻块是图」这个确定条件，不靠 endOfTextblock。
- ④ 非空段段首退格 + 上块是图 → 选中图（红，原子图无法把文字并进去，故选中而非合并）。
- **移除 `.use(trailing)` + import**：trailing 强制文末空段、导致「图作末块时下方空段删不掉」。文末续写由 `onClickBelowContent`（点正文下方补段落）+ gapcursor 覆盖。**注意这是全局行为变化**（所有文档文末不再有强制空段）。
- 竖线宽度 2px→1.5px（用户嫌粗）。
- **遗留**：仍只处理顶层（depth===1）图片；从文本行用方向键"走到"图旁竖线依赖 gapcursor 插件/点击（已不自己用 endOfTextblock 硬接管），若实测从文本 ↑↓ 进不到图旁竖线，再议。

### 第一期实测反馈与修复（2026-06，第十一轮）⭐⭐⭐ 节点模型真正定稿 = 行内（推翻第七~十轮的块级）
> **本轮结论覆盖前面所有节点模型决策。第四~十轮在「行内 ⇄ 块级」之间反复了 6 次，最终回到行内。下面写清为什么，
> 别再回块级。** 触发：用户提出「三段式」设计（图前/图/图后，光标像普通文本一样在图两侧、退格先到图再删），
> 并发现块级方案 bug 太多（Ctrl+Shift+K 插块跳到文首等回归）。让用户先回退到稳定版。

**关键认识：用户的「三段式」设计 = 行内图片模型，是 ProseMirror 行内原子的天然行为，几乎零自定义代码。**
- 行内原子里，「图前 / 图后」就是图片**左右两侧的真实文本光标位**（竖线、贴着图）。点击图前/图后/图片本身、方向键穿行、退格「先选中图再删」、相邻空行按普通段落合并/删除——**全是 PM 自带行为**。
- 块级方案为同样的体验要写一大堆易错的自定义键处理（`handleImageKeys`/`placeCaret`/`imageGapCaretPlugin`/`imagePendingDeletePlugin` 等），还和 `trailing`、`endOfTextblock`、`Selection.near`、`GapCursor.valid` 这些不稳点缠斗 → 反复出 bug。**这是块级的根本劣势：原子块无法把相邻空段合并进去、图旁也没有「贴图的光标位」。**
- 行内唯一的老问题是「整宽图后的幻影空行」（= PM 给「行末行内图片」强制插的 `trailingBreak`<br> 另起一行）。本轮用一句 CSS 根治：`.mica-image-wrap + br.ProseMirror-trailingBreak { display:none }` —— 仅隐藏紧跟图片后的那个 br，光标改落图片右侧（行内位置），以文字结尾的段落不受影响。

**本轮具体动作（= 回退到行内 + 删掉所有块级自定义代码 + 治幻影线）：**
- `imageNode.ts` 回行内：schema `inline:true/group:'inline'/marks:''`；toDOM 外层 `span`；toMarkdown 普通图直接 `addNode('image')`（不再包 paragraph）；`transformTree` 回「块级 `<img>`html 包段落、行内就地换」；输入规则 `replaceRangeWith`→`replaceWith`。
- `createEditor.ts` **删除**：`handleImageKeys`、`placeCaret/placeCaretTr`、`gapImageSide`、`isImageNode`、`selectImageAt`、`imageGapCaretPlugin`、`imagePendingDeletePlugin`+key，及其 `.use()` 与 handleKeyDown 调用；**恢复 `.use(trailing)`+import**（去 trailing 疑似第十轮 Ctrl+Shift+K 跳文首回归的来源，回退求稳）。`enterEmbedOnBackspace` 只剩公式/行内代码（图片退格走 PM 行内原生：退格先选中图，再退才删——天然就是用户要的两步，蓝框即可，**不需要红框**）。
- `editor.css`：`.mica-image-wrap` 回 `inline-block`+`vertical-align:bottom`；独占一行居中用 `p:has(>.mica-image-wrap:only-child)`（+ 兼容带 trailingBreak 的排除法选择器）+ data-align 左右；**新增隐藏图后 trailingBreak**；删掉自绘竖线/红覆盖（mica-caret-*/mica-pending-delete/mica-img-gap）等块级残留 CSS。
- **二次删除提醒（红框）**：用户说默认不需要；行内默认就是「退格先蓝框选中、再退才删」。若以后想要「红框二次确认」可做成设置项。
- **待用户实测**：① 整宽图下方还有没有幻影线（trailingBreak 隐藏是否生效）；② 独占图是否居中；③ 图前/图后竖线、点击三段、退格两步删、相邻空行删除、存盘重开 markdown 往返。

### 第一期实测反馈与修复（2026-06，第十二轮）⭐⭐ 行内定稿后的四个补丁 + 配套 bug
> 第十一轮回行内后用户实测：幻影线已消、Ctrl+Shift+K 不再跳文首 ✅；但又暴露「纯靠 PM 原生」的四个不足。
> **行内方向不变**，本轮在其上打补丁（别回块级），并捎带修了表格/公式块两个 bug。

- **① 居中失效（只能左右）**：第十一轮的居中选择器 `p:has(>.mica-image-wrap:only-child)` + `:not(:has(>...:not(trailingBreak)))` 排除法在 WebView2 不命中 → 不居中。**简化为 `p:has(> .mica-image-wrap){text-align:center}`**（图已独占一行，段落里有图就居中），data-align 覆盖左右。
- **② 贴图竖线看不见（图角一个小黑点）**：原生 caret 只有一行文字高、贴在高图底角。**必须自绘**（第九轮自绘失败是因为绑在 gapcursor 上、几乎无 gapcursor；这次绑「光标紧贴图」的真实 TextSelection，稳）：`imageCaretPlugin` 给紧贴光标的图打 `mica-caret-before/after`，CSS `::before/::after` 在图左/右缘画与图等高竖线（wrap `position:relative` 收紧到图尺寸、`top/bottom:0`），`:has(.mica-caret-*){caret-color:transparent}` 隐原生。
- **③ 图前后能打字 → 图不独占**：`handleTextInput` 的 `typeBesideImageToNewParagraph`——光标紧贴图时输入文字转去**新段落**（图前→上方、图后→下方），图永远单独一行。比直接吞键友好（自动开新行写字），对标用户「图前后只能退格或回车」。
- **④ 删除二次确认（红框）做成设置项**：`SettingsService.EditorImageDeleteConfirm`（默认关=直接删；设置页「删除图片二次确认」开关 + `editor.config` 推 `imageDeleteConfirm`）。开启时 `handleImageDelete`：第一次 Backspace/Del 标 `mica-pending-delete`（红框+半透明红覆盖）、第二次才删；移开光标即取消。**caret 与 pending 都用 wrap `::after`，故 pending 激活时 imageCaretPlugin return null 让出伪元素**。
- **捎带修**：表格插入后光标落**第一个**单元格（之前落最后格）——`insertTable` 显式 `Selection.near(resolve(from+1),1)`；公式块/行内公式编辑框 `input.focus({preventScroll:true})`——修「公式组件出来后滚动条又上跳一段」（原生 focus 滚动叠加了 PM scrollIntoView）。
- **仍残留（已如实告知用户）**：**代码块**插入后滚动条上跳——根因是 Milkdown 的 CodeMirror nodeView 内部 `focus()` 自带滚动，无 `preventScroll` 钩子，不好干净地治；待用户确认是否还困扰再议（不冒险加投机性的滚动修正，避免引新 bug）。
- **待用户实测**：① 图居中；② 贴图竖线清晰可见（图左/右缘、与图等高）；③ 图前后打字自动开新行、图保持独占；④ 设置开/关二次确认的删除手感（红框）；⑤ 表格首格光标；⑥ 公式块不再上跳（代码块可能仍跳）。

### 第一期实测反馈与修复（2026-06，第十三轮）⭐⭐ 独占改用 appendTransaction（治 IME）+ 图前退格 + 代码块光标根因
> 第十二轮实测：居中✅、竖线✅（但太粗）、图前打字✅；暴露 4 个由「独占=handleTextInput 拦截」引出的坑。

- **竖线太粗**：CSS 宽 `2px → 1px`（与原生 caret 同细）。
- **图后打字首字母被复制（IME）**：根因——上一版用 `handleTextInput` 拦截改写段落，和拼音输入法的组合输入打架。**改用 `imageExclusivityPlugin` 的 `appendTransaction` 事后规范化**：任何把「图片+其它内容」混进一段的操作发生后，统一按图片边界把该段拆成多段（图片各独占），光标按原偏移跟随。appendTransaction 在输入/IME 提交之后才跑 → 不和输入法打架。**这同时治了第十二轮 #6「图旁粘贴另一张图，两图同段、居中错乱、再点居中也不居中」**（拆开后各自独占即正常）。删掉了 `typeBesideImageToNewParagraph` + 其 handleTextInput 接线。
- **图前退格把上一行文字移下来（#4）**：PM 默认「段首退格与上一块合并」会把图并进上一行文字（破坏独占）。新增 `backspaceBeforeImage`（handleKeyDown，先于 headingBackspace）：上一块空段→删空段；上一块以图结尾→只移光标到图后（再退走删除流程）；上一块普通文本→删其最后一个字符（退到上一行删字符）。
- **代码块光标乱跳/不生成（#7 根因找到了）**：`executeCommand` 对选区相关命令**无条件** `restoreSelectionAndFocus()`，把键盘触发时的**实时**光标覆盖成可能过期的 `lastSelection`（代码块内焦点切换时 selectionUpdated 不更新它）→ 命令落到上一个代码块。**改为只在编辑器已失焦（菜单点击 blur）时才恢复，键盘触发用实时选区**（`if (!editorFocused) restoreSelectionAndFocus(); else focusEditor();`）。
- **设置文案**：改为「图片前按 Delete、或图片后按退格时…；已选中图片时仍可直接删除」（用户确认：选中图直接删符合直觉，不拦）。
- **仍残留**：代码块插入后**滚动条上跳**仍在（CodeMirror nodeView 内部 focus 自带滚动、无 preventScroll 钩子；非必做，用户认可可暂留）。公式块的同类问题上轮已用 `preventScroll` 治好。

### 第一期实测反馈与修复（2026-06，第十四轮）⭐ 边距对齐 + IME 复制根因（appendTransaction 也要避组合期）
> 第十三轮实测：代码块光标不再乱跳✅、滚动上跳仍在（用户决定另开对话处理，不必管）；剩两个小问题。

- **图片边距/竖线戳出编辑区**：满宽图（max-width:100%）时图外 ±3px 的竖线戳出文本列、左右不对称。按用户算法把图片 `max-width: calc(100% - 6px)`（居中时左右各留 3px）→ -3px 竖线正好落在列边缘、与普通段落光标对齐，右侧也不再超出。
- **图后打字首字母仍复制（IME 真正根因）**：上一版以为「appendTransaction 在输入后才跑」就 IME 安全，**错**——组合（composition）进行中也会触发 docChanged，appendTransaction 的 `replaceWith` 重建段落 DOM、销毁 IME 组合目标节点 → 浏览器把组合中的字重新提交一次 → 复制。修法：appendTransaction 里 `if (proseView?.composing) return null` 跳过组合期；把规范化逻辑抽成 `buildImageExclusivityTr(state)`，由 `onCompositionEnd` 用 `setTimeout(0)` 在组合结束、PM 提交文本之后补做一次。
- 至此用户反馈「其他都没问题了」，第一期图片光标/独占/删除/对齐模型收口。**滚动上跳（代码块）留待用户另开对话**。

### 第一期实测反馈与修复（2026-06，第十五轮）⭐ 首行缩进破坏居中 + -6px 回归 + 方向键
> 第十四轮实测：IME 复制已修✅；但 -6px 引入两个回归，且发现「不居中」真凶是首行缩进。

- **不居中/右溢出（真凶=首行缩进）**：用户开了「段落首行缩进」，图片段落是顶层 `> p` 吃到 `text-indent:2em` → 图被整体右推（不居中、右侧超出列宽）。表格不是 `<p>` 故无此问题。修：`body.first-line-indent .ProseMirror > p:has(> .mica-image-wrap){ text-indent:0 }`。
- **去掉 -6px（修第十四轮的两个回归）**：① 选中框右侧变宽——`img max-width:calc(100%-6px)` 在 inline-block wrap 里使 wrap 比图宽，选中描边（挂 wrap）右侧多出 6px；② 幻影线复发。改回 `max-width:100%`。
- **竖线位置**：-3px（图外）在窄编辑器里会戳出编辑区（第十四轮 #1 真凶其实是这条 + wrap 变宽叠加）。改到图片边缘**内侧** `left/right:0`，加 `box-shadow 0 0 0 .5px rgba(255,255,255,.55)` 浅描边，保证压深色图也看得见、又不溢出。
- **幻影线加固**：隐藏规则从相邻选择器 `.mica-image-wrap + br`（br 非紧邻兄弟时漏掉）改为 `p:has(> .mica-image-wrap) > br.ProseMirror-trailingBreak`（图片段落里的 trailingBreak 一律隐藏），更稳。
- **方向键 #1**：高图的图前/图后被原生当成同一行内两个竖直位置，↓ 从图前落到图后而非下一行。加 `arrowOverImage`（handleKeyDown）：光标贴图时 ↑/↓ 把图片那行当整行、跳上一/下一块。
- **仍残留（已告知用户，cosmetic）**：拼音在图后打字时，**组合中**的字暂显在图正下方（因 IME 安全、组合期不重建结构），提交后 `onCompositionEnd` 才拆到新行 → 有个「跳一下」。→ **第十六轮用「光标重定向模型」根治，见下。**

### 第一期实测反馈与修复（2026-06，第十六轮）⭐⭐⭐ 图后光标重定向模型（根治拼音/IME，方案 3 定稿）
> 第十五轮实测：方向键从图前↓仍落图后、拼音位置怪（暂显图正下方、提交才跳行）。用户点破心智模型：**「图前就是上一段末尾，图后就是下一段开头打字，竖线只是个标识」**，并明确选「方案 3：把图后真的做成下一段开头」。本轮按此重写，**用 Claude Preview（`pnpm dev` 普通浏览器）真实验证了全部行为**。

**核心思路**：图片是**独占一段的行内原子**，段内只有 offset 0（图前）、offset 1（图后段尾）两个位置。**光标绝不停在「图后段尾」**——一落上去就弹到下一段段首。于是「图后打字」物理上就是「在下一段开头打字」，IME/拼音毫无特殊上下文 → 彻底消灭「首字母复制 / 暂显图正下方」（前几轮反复治不净的根因，本轮从模型上绕开）。

- **`buildAfterImageRedirect(state)`**：光标落在独占图段段尾 → setSelection 到下一段段首；下一段不存在则先插空段（trailing 通常已保证有，这里兜底）。挂在 `imageExclusivityPlugin` 的 `appendTransaction` **末尾、且不被 `docChanged` 拦**（点击/方向键这类纯选区变化也要弹），组合期 `proseView.composing` 仍跳过、由 `onCompositionEnd` 兜底补做。
- **`imageBlockBeforeCaret(state)`**：判「光标在某段段首、上一块是独占图段」= 图后的真实形态，返回那张图 atom 位置。竖线（`imageCaretPlugin` 加第三分支画 `mica-caret-after`）、删除、方向键都复用它。
- **穿行**（图前 ⇄ 图 ⇄ 图后三停）：图前=`TextSel@imgPos`、图=`NodeSelection`、图后=下一段段首。新增 `arrowLeftToImage`（图后 ← 选中图，否则默认退回图段段尾又被重定向弹回 → 卡住）；`arrowOverImage` 补「图后 ↑ → 图前」。
- **删除**：`handleImageDelete` 重写 + 抽 `imageAdjacentForDelete`，覆盖「图后退格、图前 Del」也能删到图。**关键**：不再 `if(!confirm) return false` 把活儿交回 PM 默认——默认在「下一段段首」退格只会合并段落、删不到上面的图，必须显式删。
- **验证手段（留作以后浏览器调试）**：`web/src/ipc/bridge.ts` 的 dev shim 暴露 `window.__hostSend(msg)` 模拟宿主 IPC 下发（`editor.load`/`theme.update`）；`createEditor` 在 `import.meta.env.DEV` 下把 view 挂 `window.__pmView`。`pnpm dev` 普通浏览器里即可驱动选区实测（图裂但节点结构在）。**注意**：合成 `KeyboardEvent` 只触发我们自定义的 `handleKeyDown` 拦截，PM 默认方向键（靠浏览器原生选区）合成事件下不动，得靠真键盘测。
- **实测结论（全过）**：图后段尾→重定向到下一段段首✅；图前/图后竖线✅；**图后打字落入下一段、图段保持纯图**✅（根治 IME）；图后←选中图✅；图后↑→图前✅；图后退格删图✅；图作末块自动补空段✅；无运行时报错✅。

### 第一期实测反馈与修复（2026-06，第十七轮）⭐⭐⭐⭐ 推翻行内、定为「块级原子」（重定向方案是死路）
> 第十六轮实测：重定向方案修了拼音，却引入 5 个更严重的 bug——① 图下一行开头永远看不到光标（被判成「图后」画竖线+透明原生 caret）；② 两图相邻第一张末尾点不到（弹到下一张）；③ 图后方向键多跳一行 / 右键到下一行字符后；④ 光标存在一瞬被强制搬走（appendTransaction 每次选区变化都重定向）；⑤ Ctrl+A 图片无选中框。用户洞察「光标闪一下被换走」直指根因，并提出「块+行内结合」。

**诊断**：bug ①~④ 全是「重定向」这一个架构决策造成的——行内图的「图后段尾」是原生光标看不见的位置，藏它只能靠**强行搬运光标**，按下葫芦浮起瓢，是**死路**。

**定案：图片直接做成块级原子**（不是容器套行内）。用户心智「图前=上一段末、图后=下一段开头，竖线只是标识」由此**字面成立**：光标天然停在图上下的**普通段落**里（不是从图内弹出），打字=普通段落打字 → **IME 零特殊性、根治**；Ctrl+A/点击=块级 NodeSelection、天然选中框；图前后/两图间/图首尾的光标位由 **gapcursor**（早已接入）提供。**此「块级」≠ 早期被否的「块级」**——早期想在块旁硬造「贴图行内光标位」，和 gapcursor 缠斗反复失败；现在用户接受「光标在相邻段落」，正是块级 atom 的天然形态，不用硬造。

**改动**（删掉一大堆易错自定义码：`imageCaretPlugin`/`imageExclusivityPlugin`/`buildAfterImageRedirect`/`backspaceBeforeImage`/`arrowOverImage`/`arrowLeftToImage` 全删）：
- **imageNode.ts**：schema `inline/group:'inline'`→`group:'block'`；toDOM `span`→`div`。**序列化往返坑**（mdast image 是 phrasing 永远在 paragraph 内、但要块级）：parse 时 `micaImageRemark.transformTree` 把「段落里的图」拆出提升为块级 image 兄弟；serialize 时普通图 **`openNode('paragraph')+addNode('image')+closeNode()`** 包回段落（否则 stringify 不出 `![]()`），带样式图仍 `addNode('html')`。输入规则改 delete→setSelection→replaceSelectionWith 块级图。
- **createEditor.ts**：删上述行内机制；`handleImageDelete` 只认 `NodeSelection`（二次确认）；新增 `imageSelectionPlugin`（范围选区/AllSelection 覆盖图时打 `mica-selected` 描边，解 bug ⑤——块级 atom 原生 selection 不高亮）；`onCompositionEnd` 去掉 exclusivity/redirect 补做（不再需要）。
- **editor.css**：`.mica-image-wrap{display:block;width:fit-content;max-width:100%;margin-inline:auto}`（收紧到图宽+居中，描边贴图），`[data-align=left/right]` 用 margin；删所有 `mica-caret-*`/图的 `caret-color:transparent`/`p:has(image)` 居中与 trailingBreak 隐藏/首行缩进排除（块级图不在 p 里、全失效）。
- **bridge.ts**：dev shim 加 `window.__hostSend`（模拟宿主 IPC）+ `createEditor` DEV 下 `window.__pmView`，供 `pnpm dev` 普通浏览器实测。
- **实测结论（Claude Preview 全过）**：块级 image 独占块✅；**图下一段开头光标可见**✅（bug①）；两图相邻成 image/image/段、中间走 gapcursor✅（bug②）；Markdown 往返干净 `![]()`/`<img data-align>`✅；对齐 margin✅；范围选/全选图块描边✅（bug⑤）；段中插图自动拆段✅；无报错✅。bug③④（方向键/光标闪搬）随重定向删除而消失。
> **遗留给用户真键盘确认**：图前↔图↔图后的方向键穿行、两图间 gapcursor 落点、Ctrl+A 整体观感（合成事件测不了 PM 原生方向键/gapcursor）。

### 第一期实测反馈与修复（2026-06，第二十轮）跨图边界删除/Enter 的 4 个修正（根因=合并又拆，非 IME）

#### 亚克力抽成共享变量系统（2026-06，第八轮）—— 表格/图片浮条统一、白底不再「白死」
- **动机**：① 表格浮条 `.mica-table-toolbar` 之前用 `background: var(--mica-surface)`（**纯白 #fff**）+ 写死 `rgba(128,128,128)` 灰，白底上「太白没边界」、暗色也将就；② 图片浮条的亚克力是写死在自身的 `--tb-*` 局部变量、无法复用；③ 用户将做多套主题，需可统一调。
- **关键认知（Gemini + 用户实测）**：WinUI 原生亚克力有「**亮度保护/Luminosity 混合**」——纯白背景上会折射成淡灰以保住对比度；CSS `backdrop-filter` 做不到该混合，故底色**不能用纯白 255**，否则白底上 `255*(1-α)+255*α=255`「白死」、与书写区融为一体失去边界。**正解 = 底色用偏灰白（248）+ 边线加重到 0.08**，白底上才有边界与质感。
- **实现**：在 `editor.css` `:root`（亮）+ `body.dark,.mica-table-overlay.dark`（暗）定义一组 `--mica-acrylic-*`（bg/blur/border/noise/radius/shadow + 内部交互态 hover/active/line/field-bg/stroke/track/thumb-gap）；新增共享基类 `.mica-acrylic, .mica-table-toolbar, .mica-image-toolbar { 背板模糊+底+边+影 }` + `::before` 噪点 + `> * z-index:1`。表格浮条删掉自身 bg/border/shadow 与写死灰（内部 seg/sbtn/step/select 改引 `--mica-acrylic-line/hover`，**顺带修好了它的暗色**）；图片浮条删掉自身的 surface 声明与暗色覆盖块，仅把内部 `--tb-*` **别名**到共享变量（保留下方大量 `var(--tb-*)` 引用不动）。
- **调节入口**：整体浮层质感（白/灰深浅、模糊半径、噪点、边、影、圆角）→ 改 `:root` 的 `--mica-acrylic-*`（暗色在 `body.dark` 块）；做主题时各主题覆盖这一组即可。见记忆 [[acrylic-shared-vars]]。

- **统一组件**（用户：所有浮条抽成一套、图片的额外东西全删、以后新浮条复用）：新增唯一浮条类 **`.mica-toolbar`**，表格/图片浮条 root className 都改成 `'mica-toolbar mica-xxx-toolbar'`（旧类名仅留作标识，CSS 不再针对）。图片浮条原先一整套 `.mica-image-toolbar .mtb-*`（root/row/seg/sbtn/svg 尺寸/交互态）**全部并入 `.mica-toolbar`**，只留信息行/开关/NumberBox/滑块这些图片独有控件。**冲突项以表格为准**（用户「改成和表格一个组件」）：`.mtb-seg` 用带边分段、`.mtb-active` 用强调色填充块。`.mtb-*` 子类名两浮条本就一致，故 JS 零改动（仅 2 处 className）；CSS 全局无 JS 选择器引用旧类名（已验证）。

### 第三期：裁剪面板（WinUI3 原生弹窗，存裁剪矩形不动原图）【2026-06 完成，待用户实测】
> 用户要求裁剪面板用 **WinUI3 原生**实现（区别于浮条/右键的 web 风），右键菜单 + 浮动条都加「裁剪」入口。

**模型（不动原图，只记「显示哪一块」）**：image 节点新增 `crop` 属性 = 相对**原图自然尺寸**的归一化分数串 `"L,T,W,H"`（0~1），
null=不裁。原图文件绝不改动 → 可无限次回原图重裁。crop 非默认即「带样式」→ 存 `<img data-crop="...">` HTML
（data-crop 非标准 CSS、塞不进 style；别的渲染器忽略它显示全图，原图完整 → 优雅降级）。

**显示（web，定稿为「外层 wrap + 内层 clip 盒」）**：NodeView 给 img `position:absolute` 并放大（`width:(1/W)`、
`left:-(L/W)`、`top:-(T/H)`，百分比基准内层盒宽/高），内层 `.mica-image-clip{position:absolute;inset:0;overflow:hidden;
border-radius}` 裁到可视窗。wrap `aspect-ratio:(W*natW)/(H*natH)`（NodeView 图 load 后异步设）。NodeView 动态把同一个
img 在 wrap↔clip 间 appendChild（不重载）。
- **试错记录（别再走回头路）**：① 最早 `overflow:hidden` 放 **wrap** 上 → 裁掉竖线/光标伪元素（圆角处缺一截）+ 图盖光标。
  ② 改 img 上 `clip-path:inset(...round)` + 去 overflow → 光标好了但**新增横向滚动条**（clip-path 只裁视觉、不裁布局溢出，
  放大几百 % 的绝对 img 仍撑出文档，靠右/大图/窄行必现）。③ **定稿内层盒**：overflow 收住溢出=无滚动条；竖线/光标在
  外层 wrap=不被裁、加 `z-index:1` 压在内层盒上=不被盖；圆角=内层盒 border-radius，边框/选中框圆角=wrap border-radius。
- **塌缩坑**：绝对 img 不撑开 inline-block wrap → width=null 时塌成极小框。修：`crop && !width` 时图 load 后
  `dom.style.width = round(natW*W)px`（max-width:100% 钉行宽内）。已删 `runImageOp('crop')` 旧的「强行补 px width」hack。
- **边框**：img 被裁切，边框挂 img 会被裁没 → **裁剪图边框挂 wrap**（`dom.style.border`），普通图挂 img；浮条边框即时
  预览按 `wrap.classList.contains('mica-cropped')` 决定挂 wrap/img。
- **浮条尺寸显示**：`reflect()` 按 `parseCropAttr` 算 `round(nw*W)×round(nh*H)`，显示裁剪后尺寸而非原图分辨率。
- **对话框拖动卡顿**：`CropSelector.IsDragging` 期间跳过 NumberBox 回填，松手补刷（每 move 写 NumberBox.Value 很重）。

**入口（两处，都先选中图再触发）**：
- **浮动条**（`imageToolbar.ts`）：行 3 加裁剪按钮 → `notify('host.imageCrop', {abs, crop})`（abs=磁盘绝对路径，
  网络/base64 图 abs 空 → 不发）。
- **右键菜单**（`imageSetup.ts` + `MainWindow.Image.cs`）：notify 里多带 `crop`，宿主菜单加「裁剪图片」项
  （仅磁盘图可用），点击直接调 `ShowImageCropDialogAsync(abs, crop)`。

**宿主对话框（WinUI3）**：
- `ImageCropHandler`（IPC 单例，`host.imageCrop`）→ `MainWindow.ImageCrop.cs` 的 `ShowImageCropDialogAsync`。
- 读**原图自然尺寸**用 `BitmapDecoder.CreateAsync(stream)`（**不能** await 游离 `BitmapImage.ImageOpened`——未挂可视树不解码、永久挂起）；显示用 `new BitmapImage(new Uri(abs))` → `Controls/CropSelector`
  （Canvas 叠：原图 + 区外四块暗化遮罩 + 白色选框 + 8 把手；指针：把手缩放/框内移动/框外重新框选；输出归一化矩形）。

### 第四期第 3 步：组内图浮条 / 裁剪 / 翻转 / 替换接线【2026-06 完成，待用户实测】

  - `readTargetAttrs` / `writeTargetAttrs`（patch 合并；组内图改 `images[index]` 并重选容器 + 维持激活 index；可选 `scroll`）/ `targetDom`（独立图 `nodeDOM(pos)` 即 wrap；组内图取容器内 `.mica-image-wrap[data-index=N]`）/ `deleteTarget`（独立删节点、组内删 `images[index]`，删剩激活同位下一张、删光由 cleanup 删容器）/ `sameImageTarget`。

- **触发改由插件而非 `selectionUpdated`**：新增 `imageToolbarSyncPlugin`（`createEditor.ts`，`Plugin.view().update` → `imageToolbar.sync()`）。理由：① `selectionUpdated` 里 `view.state` 慢一拍（[[table-toolbar-selection-staleness]]），而 `PluginView.update` 在状态提交后跑、`view.state` 最新；② **组内激活图切换时 PM 选区不变**（始终 `NodeSelection(容器)`，只 `imageGroupActiveKey` 的 index 变）→ `selectionUpdated` 不触发，但事务已 dispatch → `view.update` 必触发，故能捕获。`sync()` 据 `currentImageTarget` 自行推导显隐+回填。
- **`imageSetup.ts`**：`runImageOp`（裁剪/翻转/替换/删除/对齐回传）改用 `currentImageTarget` + `writeTargetAttrs`/`deleteTarget`，组内图自动命中（右键时已 `setMeta` 激活）。右键菜单加**组内分支**：`groupPosFromDom`（`nodeDOM` 全等比较定位容器节点位置）+ `wrap.dataset.index` → 选中容器 + 设激活 → `host.imageMenu{…,grouped:true}`。
- **宿主菜单**：`host.imageMenu` 多带 `grouped`；`ImageMenuHandler` 解析、`MainWindow.Image.cs` 的 `ShowImageContextMenu` 在 `grouped` 时**隐藏「对齐」子菜单**（组内对齐无意义）。

**待用户实测**：① 点组内某图 → 浮条浮在该图上方、圆角/边框/翻转即时生效；② 切换激活图（点另一张/方向键）→ 浮条跟着换绑；③ 组内图裁剪（右键/浮条）→ 弹原生对话框、回写只改那张；④ 右键组内图 → 无「对齐」项、替换/删除/裁剪可用；⑤ 独立图浮条/右键全部不回归。

#### c2 拖拽**第二轮**修复【2026-06，待实测】（第一轮没根治，又报 7 点）

> **核心根因（一统多 bug）**：第一轮只把图片/图册 schema 设 `draggable:false`，但 **contenteditable 里浏览器仍会对文本/元素发起原生 HTML5 drag**。原生 drag 一旦启动就**劫持指针**——`mouseup` 不再触发（改 `dragend`），于是自绘拖拽的 `onUp` 永不执行：图保持选中、松手不落、要再点一次才落（第二次 mousedown 的 mouseup 才触发遗留的 onUp），一路显示 ⊘，且把图册内容做成**原生选区**（`::selection` 灰底 → 整组变灰变暗）。这一个根因同时造成反馈 1/2/4/5。
>
> **根治**：`createEditor` 直接在 `wysiwygEl` 上挂原生 `dragstart` 监听、**一律 `preventDefault`**（编辑器内不用任何原生 drag，全走自绘指针拖拽）。原生 drag 从源头不启动 → mouseup 正常 → 自绘拖拽可靠 → ⊘/卡死/变灰全消。

1. **松手不落、需再点一次**（根因见上）→ `dragstart` 全局 `preventDefault`。
2. **同 1**（同根因）。补充：原 `dragover/drop` 走 PM `handleDOMEvents` 会被图册 NodeView 的 `stopEvent:true` 吞掉、对外部文件不可靠 → **改挂 `wysiwygEl` 原生 DOM 事件**（`onEditorDragStart/Over/Drop`）。
3. **落点指示太粗的横线** → 弃「挂 body 的横线」，改 **widget decoration 占位条**（`.mica-image-drop-spacer`，虚线高亮带）插进文档流：自然**把下方内容往下推**、明确示意落点（对标 Notion）；in-flow → 不必处理 body 的 CSS zoom 坐标换算，且能落到**任意嵌套深度**（见 7）。位置由 `imageDrag` 经 `imageDropKey` meta 通知 `imageDropSpacerPlugin` 渲染（纯 decoration、不改文档不进历史）。
4. **选中图册/组内图导致整组变灰变暗** → 根因是原生选区 `::selection`（灰底 `rgba(120,120,120,.3)`）罩在图上。① 根治原生 drag（不再做原生选区）；② `.mica-image-group` / `.mica-image-wrap` 加 `user-select:none` 兜底。**未动选中描边视觉**（用户明确要求别乱改）。
5. **资源管理器拖图仍 ⊘**（历史顽疾）→ 根因：① PM `handleDOMEvents` 被 NodeView `stopEvent` 吞、② `types.includes('Files')` 这类条件在 WebView2 dragover 期可能不命中。**改挂原生 DOM 监听 + `dragenter`/`dragover` 无条件 `preventDefault`**（内部已无原生 drag，故只会是外部文件）。WebView2 默认 `AllowExternalDrop=true`，无需改宿主。

### 第四期第 9 步：图册 layout 切换 + 多行排列（justified 保序 / masonry 不保序）【2026-06 完成，待用户实测】

> 用户拍板：多行**可直接用现成排版引擎、不必自写贪心分行**，要**保序**与**不保序**两个版本；空单图占位不做。
> 关键决策＝**纯 CSS 实现，不引布局库、不上 ResizeObserver**——浏览器 flex/multicol 引擎随宽度（缩放/侧栏/窗口）自动重排，比「绝对定位 + 库 + ResizeObserver」更稳，也符合项目「仅用 CSS Variables / 不引 UI 框架」约定。两版正好对应两种 CSS 排版引擎。

- **`GroupLayout` 扩为 `'row' | 'justified' | 'masonry'`**（`imageGroup.ts`，后续再加 `carousel`/`magnetic`）。序列化/解析无改动——`data-layout` 本就往返，新值只是字符串；**纯 web 端、零宿主改动**。
- **保序＝`justified`（flexbox 两端对齐多行）**：容器 `flex-wrap`，每图 `flex-basis = 宽高比 × 目标行高`（`--mica-gallery-row-h` 默认 200px）+ `flex-grow = 宽高比`。数学：基准时各图宽=aspect×H、高=H；一行余量按 flex-grow=aspect 分配 → 每图终高 = H + 余量/Σaspect，**同行恒等高、整行填满**（唯一解，见 css 注释推导）。**末行不拉伸**：一个 `flex-grow:1000000` 的 `::after` 伪元素落最后一行吃掉余量 → 末行图保持自然高度、左对齐（Google Photos 式）。图左→右换行＝**保序**。
- **不保序＝`masonry`（CSS 多列瀑布流）**：`display:inline-block` + `column-width:160px`（列数随宽自适应）+ 子图 `width:100%; break-inside:avoid`；图在列内自上而下流动 → 阅读序非左→右＝**不保序**，但填充紧凑无空隙（Pinterest 式）。
- **渲染器配合（`imageNode.ts`）**：组内模式 `onMetrics` 除写 `flex-grow=宽高比`（row 等高用）外，**新增写 `--mica-aspect` 自定义属性**供 justified 的 `flex-basis` 计算。无其它改动——裁剪/翻转/圆角/显示管道对三种 layout 完全一致。
- **layout 切换工具条（`imageGroup.ts` NodeView 自掌 DOM）**：容器选中（`.ProseMirror-selectednode:not(.mica-has-active)`）或鼠标悬浮时，右上角浮出 `.mica-gallery-bar`（亚克力质感、暗色适配）：三个布局按钮（单行/多行/瀑布流，当前态强调色高亮）+ 分隔 + 隐藏边框开关（toggle `frameless`）。**绝对定位 → 不占 flex/列流**（不会被算成一张图的槽）；mousedown 阶段 `stopPropagation`+`preventDefault` 挡掉容器自身的「重设选区/起拖」，改属性走 `setNodeMarkup`、提交后保持容器选中（条不消失、可连续切）。空图册占位态隐藏（切布局无意义）。

**待用户实测**：① 选中图册→右上浮出工具条，三按钮切 单行/多行/瀑布流 即时生效、当前态高亮；② justified 多行同行等高、整行填满、末行左对齐不拉伸、缩放/拖侧栏自动重排；③ masonry 瀑布流多列紧凑无空隙、窄屏自动减列；④ 隐藏边框开关有效；⑤ 裁剪/翻转/圆角图在三种布局下都正常；⑥ 存盘往返 layout 不丢；⑦ 单行(row)原行为不回归。

## 关键约定速查

- web `<img>` DOM src 永远 = `https://img.mica.local/img?p=<encodeURIComponent(绝对路径)>`；.md 里存相对路径。
- 默认落盘 `<笔记本根>/.mica/assets/<笔记相对路径去扩展名>/`。
- 浮动条/裁剪选框等浮层用视口坐标、挂 body 外，零 z 换算（见表格大坑二）；图片浮条复用表格的 `getEditorOverlay()`。
- **图片样式存哪**：显示宽度 `width` 挂外层 `.mica-image-wrap` 的 `style.width`（img `width:100%` 填满）；圆角/边框挂 img 内联 `style`（`border:Npx solid` 用 currentColor）。带样式 → `<img>` HTML，全默认 → `![]()`。
