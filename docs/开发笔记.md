### 2026-06-28 待办勾选框与文字对不齐（中英文/大小写都要稳）
- **现象**：任务列表勾选框相对文字偏高，且中文/英文/全大写等不同内容下对齐程度不一，没法靠绝对定位通吃。
- **根因**：旧实现用 `li::before` **绝对定位**（`top:0.35em`）把勾选框锚到「行盒」。行盒中心 ≠ 文字光学中心，且不同字形（CJK vs 拉丁）在行盒里的视觉位置略有差异 → 看着对不齐。
- **修复**（`editor.css` 任务列表段）：改成**段落首行内的行内元素** `li[data-item-type="task"] > p:first-of-type::before`，`display:inline-block` + `vertical-align:middle`。`middle` 的对齐基准是**父元素字体度量**（baseline + x-height/2），**与具体填什么字无关**，故各种内容都稳定对齐。对勾改用**单元素背景 SVG**（伪元素只有一个 `::before`，`::after` 无法锚到 `::before`）。`text-decoration:line-through` 不会划到 inline-block（CSS 规范：原子行内盒不被祖先文本装饰线穿过），故对勾框不被删除线划到。点击命中逻辑（`taskCheckboxClickPlugin` 的 `clientX < rect.left + 1.5em`）不变仍成立。**教训**：要让一个行内标记跟文字「内容无关地」垂直对齐，用 `vertical-align:middle`（字体度量），别用绝对定位锚行盒。

### 2026-06-23 文件树多选模型（级联 + materialized，定稿）

- 背景：给多选加勾选框后纠结「选文件夹要不要级联选内部」。迭代了三版：① 派生「有效选中（自己∨祖先被选）」+ 置灰 → 深浅不一、普通单击也级联太吵；② 扁平互斥不变量（选文件夹只选自己、不级联）→ 用户其实**要**级联；③ 定稿＝级联 materialized。
- 教训：别「加个变量」打补丁。**显示态与选中态必须是同一个真值**，否则两套状态迟早打架。
- 定稿模型（`Views/MainWindow.FileTree.cs` 选择区）＝**单击与多选两套、互不混用**（用户坚持单击不级联）：
  - **单击**（无修饰键 + 多选模式关）→ `SelectOnly`：只选它自己、**不级联**（点文件夹只高亮该文件夹）。
  - **多选**（Ctrl/Shift 点击，或多选模式开）→ 级联 materialized：选文件夹＝把它**和所有子孙真的加进 `_selection`**
    （不是派生/置灰）。于是 `FileNode.IsSelected ⟺ ∈ _selection`（二元、统一显示、无深浅）。`SelectCascade`/`DeselectCascade`。
    规则：① 选父文件夹→内部全选；② 已选文件再选其父文件夹→父下全选；③ 取消某子项→连带取消其自身+子孙+**所有祖先**文件夹、
    **兄弟项不动**；④ 不向上自动选。
  - **单击→多选的过渡**：进入多选语义前 `NormalizeCascade()`——把已单击选中的文件夹补成级联（连其子孙）。触发点＝
    Ctrl/Shift 点击（`ToggleInSelection`/`SelectRange`）、或开启多选模式（`OnToggleMultiSelect`）。于是「单击文件夹→开多选/Ctrl 点下一个」
    会一致地把该文件夹整体选中。
  - 新建/移入「已选中文件夹」的节点也并入选中（`IsParentSelected`），维持「文件夹选中⟹子项选中」一致。
  - **操作走 `TopLevelSelection()` 去重**（集合里文件夹盖掉其子孙→只搬一次）。故「是否多选」「复制路径」「右键单/多选菜单」
    一律看 `TopLevelSelection().Count`、**不是 `_selection.Count`**——右键单选时菜单作用于那个顶层项。
  - 教训：迭代了四版（派生置灰→扁平互斥→级联全局→单击/多选分离）。**显示态=选中态同一真值**、**单击与多选别混在一套逻辑里**。

### 2026-06-23 文件树选中效果：强调色文字/图标（撤掉加粗）

- 背景：上一条修暗色时，把「选中＝文字/图标染强调色」临时换成了「加粗（`RowFontWeight` SemiBold）」（怕染色再踩 App 资源画刷的坑）。用户要的其实是**最初的强调色效果，不要加粗/变大**。
- 难点：选中是数据项的 bool 状态，要在 `DataTemplate` 里**有条件地**切 `Foreground` 到 `{ThemeResource AccentTextFillColorPrimaryBrush}`；但 WinUI 的 DataTemplate **没有 DataTrigger**，VSM 也绑不到数据项。而命令式从 `Application.Current.Resources` 取强调画刷又会重蹈暗色覆辙。
- 方案（行模板 `MainWindow.xaml`）：**叠层**。图标列/名称列各放**两个**元素——底层常规色 `{ThemeResource TextFillColorPrimaryBrush}` 常显，上层强调色 `{ThemeResource AccentTextFillColorPrimaryBrush}` 仅 `Visibility="{x:Bind SelectionVisibility}"` 时显示、同位同字盖住底层。两层都用 `{ThemeResource}` → 跟随元素主题、暗色正确，且无需「未选中」反向属性（底层恒显）。删掉了 `FileNode.RowFontWeight`。
- **别误删**：行模板里图标/名称各有「两层」是有意为之（强调色叠层）。想换选中色改上层那个 `{ThemeResource}` 即可。

### 2026-06-23 文件树暗色模式文字/图标看不清

- 现象：切到与系统相反的主题时，目录树的文字、文件图标颜色不对（深色背景上深色字 → 看不清）；而应用其余部分正常适配。用户一度怀疑是图标问题（PathIcon/ImageIcon 不变色）。
- 根因（**通用坑，会再咬人**）：应用明暗切换走的是**元素级** `RequestedTheme`（`ApplyThemePreference` 设 `Content.RequestedTheme`）。而 `FileNode.RowForeground` 和行 hover 画刷是用 `Application.Current.Resources["TextFillColorPrimaryBrush"]` 之类**命令式从应用资源取**的——`Application.Current.Resources[...]` 按**应用级**主题（`Application.RequestedTheme`，启动时跟系统、之后不变）解析，**不跟随元素级覆盖**。于是系统=浅、应用被切到深时，树文字拿到的是浅色主题的「近黑」色 → 落在深色背景上看不见。与图标类型（FontIcon/PathIcon）无关；树本来就用 FontIcon（Segoe 字形），不是 PathIcon。
- 修复（`Models/FileNode.cs` + `MainWindow.xaml` 行模板 + `Views/MainWindow.FileTree.cs`）：把颜色全部交回 XAML 的 `{ThemeResource}`（它跟随元素主题重解析）。① 文字/图标 `Foreground` 直接写 `{ThemeResource TextFillColorPrimaryBrush}`；② 选中态不再染色，改 `RowFontWeight`（选中=SemiBold，主题无关）+ 把多选高亮底 Opacity 提到 0.12；③ hover 从「代码里 set `Grid.Background`」改成模型 `IsHovered` → 行模板里一个 `{ThemeResource SubtleFillColorSecondaryBrush}` 的 Border（`FileNode.HoverVisibility` 驱动；`ElementPrepared` 复用行时重置 `IsHovered`）。删掉了 `RowForeground` / `RowHoverBrush` / `_transparentRowBrush`。
- **教训**：用元素级 `RequestedTheme` 时，**别再用 `Application.Current.Resources[...]` 取主题画刷**塞给 UI；颜色尽量留在 XAML 用 `{ThemeResource}`，必须命令式时也要从「在世元素」的已解析资源取，而非 App 级。

### 2026-06-19 图片组：点容器右侧光标跳下一行 + 删除无二次确认

- 现象①：选中图片组里某张图后，左键点**容器右侧/内边距空白**，光标跳到了下一行；点左侧正常（落容器左缘）。
- 根因①：NodeView 用 DOM `mousedown` + `preventDefault` 自己 dispatch 选区，但 PM 自己的 mouseup 命中判定随后**覆盖**了我们的选区——点在图上时 PM 也判成选中该原子（与我们一致，不覆盖）；点在内边距/右侧空白时 PM 的 `posAtCoords` 把它判成「容器后的文本光标」（offset 1），而容器是满宽行内元素 → 该光标落到下一视觉行。`preventDefault` 只挡原生选区、挡不住 PM 自己的命中。
- 修复①-a（`web/src/editor/imageGroup.ts`）：给 NodeView 加 `stopEvent: () => true`，让 PM **忽略容器内的鼠标事件**，选区由我们的 mousedown 掌控。键盘事件 target 是编辑器根（不在 NodeView 内），故删除/方向键不受影响。这解决了点**容器内**内边距/空白的覆盖。
- 修复①-b（`web/src/editor/createEditor.ts` `clickAfterImagePlugin`）：但点**容器右缘之外**（编辑器留白）仍会被 PM 命中测试误判到「下一段开头」→ 光标跳下一行。根因是独立图独占段**居中**（两侧有空白，点右空白原生就落 offset 1），而图片组**满宽**（width:100%、两侧无空白）。新增 `handleClick`：据点击坐标找「点击点垂直区间内、整个在其左侧」的图类节点（`view.nodeDOM(pos)` 取 rect），把光标矫正到它之后（offset 1，容器右缘 → imageCaretPlugin 画竖线）。满宽单图同理受益。
- 现象②：设置开了「图片删除二次确认」，但删组内图 / 删整个容器都一次就删、无红框提醒。
- 根因②：`deleteActiveGroupImage` 直接删、根本没读 `imageDeleteConfirm`；整容器删虽走 `handleImageDelete`（确实是两步）但 `imageDeletePlugin` 的红框装饰被 `node.type.name !== 'image'` 挡掉、看不到反馈。
- 修复②（`web/src/editor/createEditor.ts` + `imageGroup.ts` + `editor.css`）：① `imageDeleteKey` 状态扩 `index?`（标某张子图待删，子图非 PM 节点 → 经 node decoration 的 `spec.micaPendingDeleteIndex` 传给 NodeView 标红那张，`data-pdel` 塞 attrs 确保重渲染）；② `imageDeletePlugin.decorations` 分三路：独立图红框 / 容器整体红框（class 由 PM 应用到 NodeView dom）/ 容器内子图（走 spec）；③ `deleteActiveGroupImage` 开确认时第一次只标红、第二次才删（切图/移光标令 `selectionSet` 清待删 → 自动取消）；④ CSS 加 `.mica-image-group.mica-pending-delete`（整容器红框）和提高特异性的子图红框（压过同时存在的激活蓝框）。
- 补丁（同日）：整容器待删时同时是 `ProseMirror-selectednode`（蓝框+蓝底）又是 `mica-pending-delete`（红框）→ 出现「两层框 + 蓝底」。改：选中蓝框规则加 `:not(.mica-pending-delete)` 关掉蓝；容器红框改用 `::after` 半透明红覆盖（`z-index:2` 压在子图上），与单图/子图待删完全一致。

### 2026-06-04 鼠标拖选向左越过行首会窜选到上一行

- 现象：在编辑器里按住鼠标拖动选择，**即使不往上移**，把指针拖到当前行行首左侧的空白处时，选区会突然把上一行也选进去。「刚越过行首一点点」时正常，再往左才出问题。
- 根因（用 `caretRangeFromPoint` 在浏览器里复现确认）：旧布局 `.milkdown { max-width; margin:0 auto }` 把**可编辑元素**居中成一条窄列，文本左侧的大片空白落在可编辑元素**之外**。Chromium 对「可编辑元素外」的点做粗粒度命中测试，返回的是**块与块之间的边界**（DOM 里 `editor` 容器的 child 边界，offset=上一段后/下一段前），而非当前行行首；拖选时该边界被解析到上一段末尾 → 选区窜上一行。指针只要 x 落在可编辑元素左边界之外就触发（之前那次「修过」只是改了表象，没动这个布局）。
- 修复（`web/src/styles/editor.css`）：**把横向留白全部移进可编辑元素内部**。去掉 `.milkdown` 的 `max-width`/`margin:0 auto`，让 `.milkdown` 与 `.editor`（ProseMirror contenteditable）铺满整宽；改由 `.milkdown .editor` 的 `padding: 24px max(48px, calc((100% - var(--mica-editor-width))/2))` 把文本列居中。body 也去掉横向 padding（`body{ background }` 只留底色）。源码 textarea `.mica-source` 同样改成铺满 + 同款 padding 居中（去掉 max-width+margin auto），保持两视图横向对齐。验证：改造后整条左侧空白的 `caretRangeFromPoint` 都稳定落在当前行行首，死区归零。

### 2026-06-04 无笔记时收起编辑区，露出干净 Mica 背景

- 需求：没有打开任何笔记时，编辑区的白色 WebView 画布很突兀，改成整体收起、透出 Mica 背景，正中放一行淡色提示。
- 实现（就是「隐藏整个面板」这么简单）：`MainWindow.xaml` 把 `FilesView` 里那层编辑区 Grid 命名 `EditorPanel`，并在它**外面**（`FilesView` 直接子节点、与面板平级）放一个居中淡色 `EditorEmptyState`（`TextFillColorTertiaryBrush`，默认 Collapsed）——提示必须放在面板外，否则面板一隐藏提示也跟着没了。`MainWindow.Tabs.cs` 的 `UpdateEditorChrome()` 按 `EditorTabs.TabItems.Count` 把 `EditorPanel` 与 `EditorEmptyState` 互斥显隐。`EditorTabs` 去掉了原来的 `Visibility=Collapsed` 默认值（面板隐藏时它自然不可见，有笔记时就该显示）。
- **启动初值坑**：本次没恢复任何标签时在 `RestoreActiveNotebook` 末尾补调一次 `UpdateEditorChrome()` 收成空状态。
- **踩过的坑：不要把显隐挂在 `TabView.TabItemsChanged` 上**。第一版把 `UpdateEditorChrome()` 放进 `TabItemsChanged` 事件，结果「双击笔记没反应、永远显示空状态」。根因：**WinUI 的 `TabView.TabItemsChanged` 对「直接操作 `TabItems` 集合（`.Add/.Remove`）」触发不可靠**（旧代码的会话持久化能跑，是因为 `SelectionChanged` 也调了 `PersistOpenTabs`，从没真依赖过这个事件）。正解照搬原设计——在**每个增删标签的位置直接调用** `UpdateEditorChrome()`：`OpenNoteAsync`（加）、`EditorTabs_TabCloseRequested`（关）、`OnCloseCurrentTab`（Ctrl+W 关，EditorTheme.cs）、`CloseTabsUnder`（删笔记/文件夹时，FileTree.cs）。后两处原本残留 `EditorTabs.Visibility=Collapsed` 的老写法（现在 `EditorTabs` 在 `EditorPanel` 内，切它会露出空面板而非空状态），一并改成 `UpdateEditorChrome()`。

### 2026-06-04 笔记本表单字数提示 & 重命名同步

**字数提示在没到上限时就「报警」**
- 现象：编辑一个旧笔记本时，名称还没打到 20 字红字提示就出现了。
- 根因：误会——`TextBox.MaxLength` 是**内建硬限制**（按 UTF-16 字符计，中文算 1 个字，不是 2），但它**只拦手动输入、不裁剪预填文本**。旧笔记本的名字是限制加入之前创建的（>20 字），编辑时整段塞进框里，`Text.Length>=20` 自然触发旧版那个布尔红字提示。
- 修复：`MainWindow.Notebooks.cs` `ShowNotebookFormAsync`，把布尔红字换成**实时计数 `N/20`**（`UpdateNameCounter`/`UpdateDescCounter`，达到上限变红、否则次要色）。硬限制仍交给 `MaxLength`，不自己数。这样编辑超长旧名会显示 `25/20` 变红，一眼看出已超限需删减，不再「误报」。重命名对话框 `MaxLength` 也从 50 收齐到 `NameMaxLength=20`。

**重命名当前笔记本后，标题栏切换器名 + 侧栏工作区头不更新**
- 现象：改了名，卡片更新了，但顶部 `VaultNameText` 和侧栏 `SidebarNotebookName` 还是旧名。

### 2026-06-03（五）关闭按钮 ToolTip 改 Ctrl+W

**TabViewItem 关闭按钮的 hover 提示从「(Ctrl+F4)」改为「(Ctrl+W)」**
- 根因：提示文字硬编码在 WinUI 内部资源，没有 `CloseButtonToolTip` 之类公开属性；(Ctrl+F4) 由内置快捷键拼出，改不动。
- **踩坑（重要）**：第一版按某 AI 建议子类化 `MicaTabViewItem : TabViewItem` → **标签头/标题整个不渲染**（空白标签）。原因：WinUI 模板控件按「自身类型」查找默认样式，子类 `MicaTabViewItem` 找不到 `TabViewItem` 的默认样式 → 没模板。要子类化就得在构造里 `DefaultStyleKey = typeof(TabViewItem)`。**结论：不要为这种小改动去子类化模板控件。**
- 最终修复（官方仓库 #8719/#4930 推荐 + 安全收尾）：仍用**原生** `TabViewItem`，在 `OpenNoteAsync` 创建时挂 `tabItem.Loaded += OnTabItemLoaded`；`OnTabItemLoaded` 用 `VisualTreeHelper` 找模板里固定命名 `"CloseButton"` 的按钮，`ToolTipService.SetToolTip(...)` 覆盖为「关闭标签页 (Ctrl+W)」。找不到就静默跳过——最坏只是提示没改成功，绝不影响标签渲染。
- 备注：Ctrl+F4 内置快捷键仍可用，只是不再显示；若要彻底去掉提示把 SetToolTip 传 null 即可。

### 2026-06-03（一）Bug 修复

**笔记本切换器悬停预览「透出」底下编辑器文字**
- 根因：预览卡片用了半透明的卡片画刷 `CardBackgroundFillColorDefaultBrush`（Fluent 卡片本意是叠在 Mica 材质上），而它悬浮在编辑器正文之上，正文就透了出来。不是层级问题。
- 修复：`NotebookPreviewTemplate` 根 Grid 底色改为不透明的 `SolidBackgroundFillColorBaseBrush`（`MainWindow.xaml`）。
- 教训：**任何悬浮在编辑器正文上的卡片/弹层都不能用 `CardBackgroundFillColorDefaultBrush`**，要不透明就用 `SolidBackgroundFillColorBaseBrush`。

**段落菜单快捷键（Ctrl+1~6 / Ctrl+0 / Ctrl+Shift+Q/K）全部失效**
- 根因：编辑器（WebView2）持有焦点时，顶部菜单栏的 XAML `KeyboardAccelerator` **收不到这些按键**——键被 WebView2 拦在 web 侧。格式菜单的 Ctrl+B/I 能用，是因为它们本就由 Milkdown 在 web 内部绑定（菜单只显示文字）。段落这些用的是真 XAML accelerator + web 端没有对应键位 → 全挂。**与「设置/笔记本页隐藏菜单 + InEditorView 守卫」无关**：守卫在编辑器界面里恒不拦截（`InEditorView` 此时为 true）。
- 修复：① `EditorHostView` 初始化设 `CoreWebView2.Settings.AreBrowserAcceleratorKeysEnabled = false`（顺带放行被浏览器占用的 Ctrl+数字/缩放等）；② 在 `createEditor.ts` 用 ProseMirror `keymap`（`paragraphKeymap`）于 web 端绑定这些快捷键，调用既有命令；③ 段落菜单的真 accelerator 改成纯显示文字 `KeyboardAcceleratorTextOverride`，避免两条路重复触发。
- 教训：**编辑器内的命令快捷键应在 web 端绑定**（焦点在那里），菜单只显示快捷键文字；不要依赖 XAML accelerator 把键送进 WebView2。

**编辑器 h6 标题发灰**
- 根因：`editor.css` 给 `.milkdown h6` 显式设了 `color: var(--mica-fg-muted)`（早期「h6 当弱化小标题」的约定），不是分辨率/缩放问题。
- 修复：移除该 `color`，h6 用正常文字色（仅字号最小），与其它标题一致。
